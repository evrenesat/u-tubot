# u·tubot agent guidance

u·tubot = Electric Eel (SmartTube fork) + an AI layer. Stylize the name "u·tubot" (U+00B7); identifiers use `utubot` / `u-tubot`.

- Read `ai/FORK_SURVEY.md` (why this base), `ai/CONTRACT.md` (wire contract and setup file), `ai/APP_INTEGRATION.md` (every touched upstream file, merge guide), `docs/development.md` (build and test), `DEVLOG-utubot.md`.
- The Android build needs two sibling checkouts next to this repo: `SharedModules` and `MediaServiceCore` (cygnusx-1-org, see `.github/workflows/utubot-release.yml` for the pinned commits).
- Android: flavor `stutubot`, app id `dev.utubot.tv`. `./gradlew :smarttubetv:assembleStutubotDebug :common:testStutubotDebugUnitTest` with a JDK 25 and the Android SDK (`JAVA_HOME`, `ANDROID_HOME` or `local.properties`).
- Identity: the `stutubot` flavor is u·tubot, never Electric Eel or SmartTube (they are credited in About and the README, not advertised): name, icons and every link it shows (releases, issues, repository) are ours. Brand SVG sources are in `assets/brand/`; `uv run assets/brand/render.py` regenerates the flavor's PNGs and the previews. Keep the README disclaimer (unofficial, not affiliated with Google or YouTube).
- AI code lives in `...common.utubot` / `...tv.utubot`; keep hooks in upstream files small and listed in `ai/APP_INTEGRATION.md`.
- Backend: `ai-backend/` (own `AGENTS.md`, `README.md`, `DEVLOG.md`).
- Live server of voice control: `realtime/` (Go, `utubot-rt`; own `AGENTS.md`, `README.md`, `DEVLOG.md`; plan `ai/VOICE_CONTROL_PLAN.md`). Tests: `cd realtime && go test -race -count=1 ./...`.
- Two clients, one feature set: every new or changed AI feature is specified, built and tested for the TV app (`stutubot` flavor) and the browser extension (`extension/`, plan in `ai/BROWSER_EXTENSION_PLAN.md`) in the same pull request or in two linked ones. If one client cannot have it, `ai/CONTRACT.md` ("Clients") says which and why. A plan or pull request for an AI feature that names only one client is incomplete. Transition: until checkpoint 18 of that plan has landed, the extension side of a new AI feature is its row in the plan's parity matrix (section 3), added in the same pull request.
- Browser extension licence: `extension/` is MIT like the rest of the repository (owner decision). Other YouTube extensions (SponsorBlock, DeArrow, Return YouTube Dislike and similar, GPL-3.0 or other copyleft) may be read to learn techniques; never copy, translate or vendor their code. Copy code only from MIT, BSD or Apache-2.0 sources, with attribution in `extension/THIRD_PARTY.md`.
- The app ships no backend address: users import a setup from their own server. Never bake a personal host, token or key into the tree; `-PutubotUrl` / `utubot.properties` are for private builds only.
- Release signing key: never commit it. It is read from `UTUBOT_KEYSTORE`, `UTUBOT_KEYSTORE_PASSWORD`, `UTUBOT_KEY_ALIAS`, `UTUBOT_KEY_PASSWORD` or a gitignored `keystore.properties`. An update signed with another key will not install over the current one.
- Branches: `main` is the default branch and work lands on it through pull requests from `feat/*`/`fix/*` branches. `master` only mirrors Electric Eel (never commit u·tubot work to it). Remotes: `electriceel` (base), `smarttube` (upstream). Sync: merge `electriceel/master` into `master`, then `master` into a branch cut from `main` and open a PR. Prefer guarding inherited upstream workflows with `if: github.repository == ...` over editing them, to keep syncs clean.
- Commits `<type>/<scope>: <imperative summary>` + bullets, no AI attribution. No secrets in git. Keep docs generic: placeholders like `utubot.example.com`, `127.0.0.1`.
- CI and releases: `.github/workflows/utubot-ci.yml` (path-filtered backend and app tests, one conclusion per commit) and `utubot-release.yml` (signed APKs + `release.json`). A merge to `main` that touches the app releases automatically; versions come from `utubot.version` plus a patch counter and `versionCode` is derived from the name (`docs/development.md`, Versions and Releasing). Keep workflow SHAs pinned; sibling pins live in `.github/actions/android-env/action.yml`. Backend deployment is the owner's own pipeline, not part of this repo.
- Tests and emulator checks never contact YouTube (nor any other real service): use the unit tests, `scripts/emulator_mock_backend.py`, local
  media and the debug-only captions harness (`docs/development.md`, "Checking the HQ captions"), and keep the emulator in a network namespace with no route out.
  Real YouTube access happens only in production (the deployed backend): never from tests, CI, emulators or an agent's verification runs. To exercise
  videos end to end without it, run the backend with `[youtube] offline` (it answers from caches and recorded fixtures, `docs/development.md`,
  "Offline mode") and, to add a video, record a fixture with `uv run utubot youtube-record` — owner only, never an agent.
